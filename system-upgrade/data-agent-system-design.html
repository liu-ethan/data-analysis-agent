page 1 / architecture flow

结果先行：做一个受控的可信问数闭环。

DataAgent 的核心不是让大模型直接写 SQL，而是用 LangGraph 编排 LLM 节点、规则节点和受控工具，让自然语言问题经过意图、口径、Schema、SQL、安全、成本、执行、验证和追溯，最终返回可解释的数据结果。

page 2 / technical detail

分点设计：每个模块都要回答一个技术难题。

第一版保持可实现：真实数据库只做 MySQL；Milvus 只做 RAG 检索层；SQL 只允许 SELECT；分库分表先做规则模拟和设计说明。重点是把 AI 应用开发链路做完整，能用 Trace 和评测支撑面试追问。

回流程 ↑

元数据与指标中心

rules

结果：MySQL 作为事实源，统一管理表字段、指标口径、表关系、权限、敏感级别和分区字段。

  • 解决业务指标口径不一致、字段含义不清、Milvus 索引与真实 Schema 不一致。
  • 规则指标版本、生效状态、字段存在性、权限策略、表关系必须走确定性查询。
  • 边界LLM 不能自己创造指标口径，也不能把向量检索结果当成事实源。
  • 数据建议准备 8-12 张业务表、60-120 个字段、10-20 个指标定义用于评测。

意图理解与澄清

hybrid

结果：把用户问题转成 AnalysisSpec，并判断是否需要 HITL 澄清。

  • 解决“今天的数据”“最近表现”“高价值用户”等问题缺少指标、时间、维度或口径。
  • LLM负责自然语言解析、多轮改写、意图分类和候选槽位提取。
  • 规则关键槽位缺失、指标冲突、时间范围缺失、大结果风险触发澄清。
  • 边界模糊问题不能靠模型猜；能改变 SQL 语义的缺口必须显式暴露给用户。

权限感知 Schema RAG

hybrid

结果：在用户可见范围内，用 Milvus 召回候选表、字段、指标文档和 SQL 示例。

  • 解决完整 Schema 注入成本高、相似字段干扰、字段幻觉和未授权元数据泄露。
  • LLM可用于候选字段语义判断和召回结果解释，但不决定权限。
  • 规则权限过滤必须发生在 Prompt 组装前；字段、表、指标都要回 MySQL 校验。
  • 数据评测 Table Recall@K、Column Recall@K、Prompt Token 降幅和未授权召回率。

Schema Linking 与 JOIN 路径

rules

结果：从候选 Schema 中得到最小可用上下文，并补全跨表查询所需关系。

  • 解决只召回相似表会漏掉维表、桥接表、映射表，导致 SQL 无法正确 JOIN。
  • 规则基于 table_relations 做关系图搜索，检查 JOIN 路径是否存在和粒度是否合理。
  • LLM可以解释为什么某张表相关，但不能凭空建立不存在的表关系。
  • 边界第一版不追求复杂血缘系统，先覆盖常见一对多维表关联。

MySQL 查询规划

guard

结果：在 SQL 生成前判断查询类型、时间范围、分区条件、分页和大结果风险。

  • 解决千万级表上无时间范围、全表排序、大表 JOIN、明细全量返回等资源风险。
  • 规则明细查询强制分页；图表限制点数；没有时间范围时澄清或使用受控默认窗口。
  • LLM辅助判断用户想要明细、聚合、图表还是导出。
  • 数据建议设置最大返回 1000 行、图表最大 200 点、超时 10-30 秒，均作为待验证参数。

SQL 生成

llm

结果：LLM 只基于受控上下文生成 MySQL SELECT，并输出使用的表字段摘要。

  • 解决自然语言到 SQL 的表达转换，同时避免全库 Schema 注入。
  • LLM生成 SQL、解释字段选择、对可修复错误做有限定向修复。
  • 规则SQL 生成后不能直接执行，必须进入 AST Policy Engine。
  • 边界第一版只支持 SELECT；不支持 UPDATE、DELETE、DDL 和任意数据库方言。

SQL Policy Engine

guard

结果：用 AST 规则和权限表拦截危险 SQL、越权字段、敏感数据和结构绕过。

  • 解决LLM 生成 SQL 不可信、字符串检查容易被 CTE、UNION、子查询、多语句绕过。
  • 规则sqlglot 解析 AST，检查表字段白名单、函数白名单、LIMIT、租户条件和只读语句。
  • 兜底只读 MySQL 账号、查询超时、最大结果集限制，防止上层规则漏判。
  • 数据评测危险 SQL 拦截率、越权拦截率、正常 SQL 误拦率。

执行、结果治理与验证

hybrid

结果：只读执行 SQL，返回表格、图表、口径说明和风险提示，不把大结果一次性推给前端。

  • 解决SQL 能执行但语义错、JOIN 放大、空结果可疑、图表点数过多和数据新鲜度不明。
  • 规则校验指标表达式、必要过滤条件、返回粒度、行数、空结果和数量级阈值。
  • LLM只基于查询结果生成简短结论，不允许脱离数据编造业务原因。
  • 边界不能证明业务因果，只能证明当前 SQL、口径和数据结果是否可追溯。

LLM 与规则的分工矩阵

boundary
事项 大模型适合做 规则系统必须做 技术难题
意图理解 解析自然语言、多轮改写、提取候选槽位。 检查必填槽位、指标冲突、时间范围和大结果风险。 模糊问题不能靠模型猜。
Schema Linking 辅助判断候选表字段的语义相关性。 权限过滤、字段存在性、JOIN 关系、Schema 版本校验。 召回相关不等于 SQL 可用。
SQL 生成 根据受控上下文生成 MySQL SELECT。 AST 安全校验、权限校验、LIMIT、EXPLAIN、超时控制。 生成结果不能直接信任。
结果解释 把表格和图表转成简短结论。 口径、粒度、空结果、数量级、数据新鲜度检查。 执行成功不等于可信。

存储架构与关系图边界

storage
组件 存储内容 为什么这样放 不负责什么
ecommerce_demo MySQL 订单、用户、商品、支付、退款、城市维表等模拟业务数据。 真实执行数据库限定 MySQL，便于体现索引、EXPLAIN、只读账号、分页和慢查询控制。 不存 Agent 的指标口径、权限策略和 Trace 主数据。
data_agent_meta MySQL meta_tables、meta_columns、column_aliases、business_terms、metrics、metric_versions、role_permissions、query_trace、query_tasks、eval_cases、eval_results。 这些是结构化事实，需要精确查询、版本管理、权限过滤、排序分页和审计，MySQL 比 MongoDB 更适合第一版。 不做向量相似度检索。
table_relations source_table、source_column、target_table、target_column、relation_type、business_meaning、is_active。 JOIN 关系是确定性 ER 信息，应该存在 MySQL 元数据中心；在线加载成内存图，用 BFS / 最短路径补全本次必要 JOIN 边。 不依赖 Milvus 相似度来判断表能否 JOIN。
Milvus 表文档、字段文档、指标文档、业务术语、查询示例，以及可选的失败案例摘要 embedding。 Milvus 只解决语义召回：根据本次 AnalysisSpec 找相关表字段和示例，不作为权限、指标或关系图事实源。 不存完整 Trace，不存权限规则，不存指标版本主数据。
query_trace question、analysis_spec JSON、retrieved_schema JSON、generated_sql、policy_result JSON、explain_result JSON、execution_status、row_count、error_type、final_answer。 Trace 有半结构化内容，但 MySQL JSON / TEXT 足够承载；常查字段单独列化，方便按用户、状态、错误类型和时间检索。 不为了 Trace 单独引入 MongoDB，避免架构发散。

第一版边界与面试口径

scope
边界 第一版做法 为什么合理
数据库 只支持 MySQL，使用只读账号和模拟经营分析库。 项目重点是可信问数链路，不是多数据库适配器。
RAG Milvus 存向量召回材料；MySQL data_agent_meta 存结构化事实、Trace 和 table_relations。 语义召回、确定性事实和审计追踪分离，能回答权限、口径、JOIN 与 Trace 追问。
关系图 不做完整 GraphRAG；从 MySQL table_relations 加载内存 Schema Graph，按需补全 JOIN 路径。 ER 关系不是相似度问题，确定性图搜索比向量召回更稳，也能减少多余表字段进入 Prompt。
分库分表 先做分片键、时间范围、跨分片风险的规则识别，不做真实中间件。 能体现大数据意识，工作量仍符合校招生项目。
写操作 不支持写 SQL，只支持 SELECT。 分析 Agent 的核心是可信查询，写操作需要独立审批和回滚链路。
评测 自建 100-200 条评测集，按简单、中等、困难分层统计。 避免只展示 Demo，能用数据说明模块效果与边界。
面试叙事可以围绕一句话展开：我没有让大模型裸连数据库写 SQL，而是把 LLM 放在受控链路里，用 MySQL 业务库与 data_agent_meta 保存事实源和 Trace，用 Milvus 做语义召回，用内存 Schema Graph 做 JOIN 路径补全，再通过 LangGraph 状态机、MCP 受控工具、AST Policy、EXPLAIN 成本检查和评测闭环共同保证问数过程可控、可追溯、可验证。
