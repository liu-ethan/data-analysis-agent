core questions

面试官最可能抓住的主线

这些不是功能清单，而是项目能不能站住的根问题。后续写代码时，每个模块都应该能回应其中至少一个问题。

大规模 Schema 下怎么找对表和字段？

SCHEMA

表多、字段多、命名相似时，错误往往发生在 SQL 生成之前。

  • 完整 Schema 无法全部注入 Prompt，Token、延迟和干扰都会上升。
  • 相似字段容易混淆，例如金额、状态、时间字段在多张表里重复出现。
  • 只找语义相似表，可能漏掉 JOIN 必需的桥接表。
  • 字段注释缺失或不准确时，模型可能根据字段名猜测业务含义。

业务指标口径怎么保证一致？

METRIC

用户说的是 GMV、退款率、活跃用户；数据库里是字段、枚举值和过滤条件。

  • 同一个指标可能存在多个口径版本，结果差异会很大。
  • 时间语义可能不明确：下单时间、支付时间、退款时间都可能合理。
  • 指标可能依赖隐含过滤条件，例如取消订单、测试订单、退款订单。
  • 用户问题缺少关键槽位时，直接猜测会让结果不可解释。

SQL 安全和权限怎么做？

SAFETY

LLM 生成的 SQL 默认不可信，不能把“能执行”当成安全边界。

  • 可能生成 DDL、DML、多语句、危险函数或高风险子查询。
  • 未授权表、字段、敏感列可能在 Prompt 阶段就已经泄露。
  • 列级、行级、租户级权限会影响可见 Schema 和 SQL 条件。
  • CTE、UNION、子查询、注释等结构可能绕过浅层字符串检查。
schema linking

Schema Linking 的真实困难

这个模块最能体现 AI 应用开发能力。难点不是“召回 TopK”，而是能否在有限上下文里找到一组足够完成查询的表、字段、关系和业务解释。

字段规模与字段幻觉

FIELD
  • 字段数量过大时，无法把所有字段名、类型、注释、枚举值完整注入。
  • 模型面对 `amount`、`pay_amount`、`actual_amount`、`refund_amount` 这类相似字段容易误选。
  • 字段名短、缩写多、英文拼音混用时，语义匹配会变得不稳定。
  • 字段说明和真实业务含义可能不一致，召回正确字段仍可能生成错误 SQL。

表召回率与跨表问题

JOIN
  • 用户问题可能涉及订单、用户、商品、地区、支付等多个业务域。
  • 语义最相似的表不一定是最终 SQL 需要的表。
  • JOIN 桥接表、维表、映射表经常不出现在用户问题里。
  • 多表 JOIN 可能导致粒度变化和重复计数，召回阶段很难只靠相似度判断。

Milvus RAG 的边界

RAG
  • Milvus 适合召回表说明、字段说明、指标说明和历史案例，但不适合作为权限和指标事实源。
  • 向量相似度不能回答“用户是否有权访问某字段”这类确定性问题。
  • 如果元数据变更后向量索引没有同步，召回结果会引用过期 Schema。
  • 检索结果进入 Prompt 前，需要考虑是否包含未授权或敏感元数据。

结构化元数据一致性

META
  • MySQL 中的表结构、字段说明、指标定义、权限规则和 Milvus 中的向量文档可能不一致。
  • 指标口径、字段注释、表关系存在版本变化时，需要知道当前查询使用的是哪个版本。
  • 同一个字段可能在不同业务域有不同含义，简单文档切片会丢失上下文。
  • 元数据质量差时，Agent 的错误会表现为 SQL 错，但根因可能是数据字典错。
mysql at scale

千万级 MySQL 数据下的新问题

数据源限定为 MySQL 是合理的，但项目仍然要体现大数据意识：不能把数据库当成无限算力，也不能把前端当成无限容器。

查询成本不可控

COST
  • 用户没有给时间范围时，SQL 可能扫描整张千万级表。
  • 排序、模糊匹配、大表 JOIN、去重聚合都可能造成慢查询。
  • SQL 语法正确不代表执行计划可接受。
  • 查询资源失控会影响真实业务库或只读副本稳定性。

结果集不能全部返回

RESULT
  • 明细查询可能返回几十万到几百万行，前端无法一次性展示。
  • 图表不适合承载过多点位或过多类别。
  • 用户想看“全部数据”和系统只能返回“有限结果”之间存在产品语义冲突。
  • 导出、分页、聚合、抽样都会影响用户对结果完整性的理解。

分区、分库分表与路由

SHARD
  • MySQL 可能按时间、租户、用户或订单维度拆分数据。
  • 用户问题不一定包含分片键，查询可能退化为多分片扫描。
  • 跨库 JOIN 和跨分片聚合会让单条 SQL 执行模型变得不成立。
  • 业务库、只读副本、分析库之间的数据延迟和一致性需要被用户感知。

数据层选择困难

LAYER
  • 同一指标可能从明细表、汇总表、物化结果或指标表得到。
  • 明细表灵活但成本高，汇总表快但维度不一定满足问题。
  • 实时数据和离线数据可能同时存在，时效性差异会影响结论。
  • 数据表产出延迟、分区缺失、上游任务失败都可能让查询结果失真。
dialog & trust

多轮、可信与追溯问题

真实用户不会每次都把完整查询条件说清楚。DataAgent 还需要面对上下文继承、模糊表达、结果解释和可追溯性。

用户问题模糊

INTENT
  • 用户可能只说“今天的数据”“最近表现”“高价值用户”，缺少指标、时间、维度或过滤条件。
  • 所有模糊点都追问会打断体验，不追问又可能生成错误 SQL。
  • 同一个词在不同业务域含义不同，意图路由本身也可能出错。
  • 用户表达可能混合分析、导出、画图、解释原因等多种意图。

历史对话污染

MEMORY
  • “用今天的数据做个图表”需要继承上一轮查询状态，而不是重新理解全部问题。
  • “换成上周”“按城市拆一下”可能是覆盖旧条件，也可能是追加新维度。
  • 上一轮 SQL 错误时，后续对话可能继续继承错误状态。
  • 历史上下文过长时，完整聊天记录无法一直注入模型。

执行成功不等于结果可信

TRUST
风险类型 需要考虑的问题 面试官可能追问
语义错误 时间字段、指标口径、过滤条件、聚合粒度只要错一个，SQL 仍然可能正常执行。 你怎么证明结果符合用户真正的问题？
JOIN 放大 一对多、多对多关系可能导致金额、订单数、用户数重复计算。 为什么结果数量级看起来合理也可能是错的？
空结果 空结果可能是真没数据，也可能是字段映射、时间范围、枚举值或权限过滤错误。 用户看到空表时，系统应该如何判断原因？
数据新鲜度 今天分区未产出、上游任务延迟、汇总表未刷新都会影响结论。 结果到底代表实时数据、T+1 数据，还是缓存数据？
evaluation

不能只展示 Demo，还要能被评测

这个项目最终能不能说服面试官，关键不是“跑通一个例子”，而是能否构造失败场景、拆解错误来源，并用指标说明系统能力边界。

评测集覆盖面

DATASET
  • 只覆盖单表查询会让项目看起来像基础 Demo。
  • 多表 JOIN、指标歧义、多轮追问、权限攻击、慢查询、大结果集都需要样本。
  • 简单、中等、困难问题需要分开统计，否则平均值会掩盖复杂问题表现。
  • 安全类问题既要看拦截率，也要看正常问题是否被误拦。

错误归因困难

TRACE
  • 最终 SQL 错了，根因可能是意图解析、Schema 召回、指标口径、SQL 生成或权限规则。
  • 只看最终结果，无法知道应该优化哪个模块。
  • 两条 SQL 语法不同但结果等价时，评测不能只做字符串匹配。
  • 修复链路可能掩盖前序错误，使问题归因更复杂。

需要提前想清楚的指标

METRICS
评测维度 需要衡量的问题
业务理解 指标、维度、时间范围、过滤条件、排序、限制条数是否被正确识别。
Schema Linking 目标表、目标字段、JOIN 路径、字段解释是否被正确召回。
SQL 正确性 SQL 是否能执行，执行结果是否与标准答案语义一致。
安全权限 危险 SQL、越权访问、敏感字段泄露、高成本查询是否被识别。
大结果治理 返回行数、图表点数、分页、导出和查询耗时是否处于可接受范围。
成本性能 Prompt Token、LLM 调用次数、P50/P95 延迟、SQL 执行时间是否可解释。
